A **measurement record** for a computer-architecture experiment lists the hardware, software, method, evidence class, and results needed to reproduce and interpret a benchmark result.

A result without such a record can be neither reproduced nor checked. A minimal schema applies whether the evidence is a wall-clock timer, a hardware performance counter, or an RTL simulation waveform. Applied to the benchmark notes under `systems/operating-systems/benchmarks/`, it shows that most of them lack required fields. The gaps are reported as they are instead of filled in, since backfilling unrecorded hardware details would violate the rule in `.notes/artifacts.yml` against inventing or reconstructing unrecorded measurements.

## The measurement-record schema

Every benchmark claim in the repository should be traceable to a record with the following fields.

```yaml
## schema below: informal, not machine-validated
question: "What is being measured, in one sentence."
hardware:
  cpu_model: string           # e.g. "Intel i9-13900HK" -- exact model, not just vendor
  microarch: string           # e.g. "Raptor Lake" -- helps interpret cycle counts
  core_count: int
  cache_sizes: {l1: str, l2: str, l3: str}
  memory: {size: str, type: str, channels: int, speed: str}
os: string                    # kernel version and relevant sysctls (governor, THP, ASLR)
compiler:
  toolchain: string           # e.g. "gcc 13.2"
  flags: string                # e.g. "-O3 -march=native"
evidence_class: enum           # wall-clock | hardware-counter | rtl-waveform | analytic-model
method:
  repetitions: int
  warmup: bool
  affinity: string             # pinned core(s), NUMA node
  variance_reported: bool      # stddev, min/max spread, or CI
workload:
  description: string
  size_or_shape: string
results:
  raw_or_summary_table: table
  units: string
```

Three evidence classes cover nearly all measurements in the repository and its likely extensions.

- **Wall-clock**: `clock_gettime` or equivalent around a timed loop. It is the simplest to collect and the most susceptible to noise (frequency scaling, other processes, page faults).
- **Hardware-counter**: `perf stat`/`perf record` reading model-specific registers (cache misses, branch mispredicts, LLC references). It requires the exact microarchitecture to be recorded, because counter definitions and even counter availability vary across vendors and generations.
- **RTL-waveform**: cycle-accurate simulation output (from a simulator such as Verilator or a vendor simulator) for a specific RTL design at a specific commit, as in [[hardware/computer-architecture/rtl-reading-lab|the RTL reading lab]]. The "hardware" is then the simulated microarchitecture, not a physical chip, and the record must state this and name the simulator and commit.

`evidence_class` determines what "reproducible" means. A wall-clock number is reproducible only on the same or comparable hardware; a hardware-counter number is comparable across machines only within the same microarchitecture family; an RTL-waveform number can be reproduced from the same commit and simulator version, independently of physical hardware.

## Why the record matters: a simulation

Each field under `method` and `os` corresponds to a source of error in a wall-clock comparison. The figure simulates one comparison. Version B of a routine is 2% faster than version A, a plausible size for a micro-optimization. The harness times all of A's runs and then all of B's, as a simple shell loop would. Each control that is omitted adds a noise source that the record would have to disclose.

- **Warm-up** (`method.warmup`): the first runs incur cold caches, page faults and untrained branch predictors.
- **Pinning** (`method.affinity`): an unpinned thread sometimes migrates to another core and must refill its caches.
- **Fixed frequency** (the governor and turbo settings under `os`): turbo frequencies decline as the chip heats, so later runs execute more slowly.
- **A quiet machine**: other processes occasionally occupy the core.

<BenchmarkNoise />

With no controls and five runs of each version, the interval for the speedup spans tens of percent, and the experiment cannot distinguish the two versions. With only the warm-up enabled, the interval narrows but the estimate is biased. Thermal drift falls entirely on B because B runs second, and most repetitions of the experiment find A faster. Fixing the frequency removes that bias. Fifty runs of each version also mostly conceal it, but only because the chip reaches a steady temperature early in the session, a property of this simulated machine that does not hold in general. Interleaving A and B runs would also cancel the drift, so a complete record should state the order in which the runs were taken.

The measurement record shown in the figure lists the four controls. These are the fields that most of the repository's benchmark notes lack, and without them a reader cannot determine which of these scenarios produced a number.

The original records above lack OS/kernel details, and most omit repetition and variability. These gaps prevent checking whether an apparent difference could reflect frequency changes, scheduling, or run-to-run noise. The new store-forwarding record shows how to preserve the source and individual samples alongside the setup; its limitations still include uncontrolled frequency and background activity.

Relative comparisons also need a valid harness and controlled conditions; their size and sometimes their ordering can change across processors. Historical results should be kept separate when a new experiment is run, with enough detail recorded to distinguish the observed behavior from its proposed explanation.

## What a complete record looks like

The `cache_line_efficiency` benchmark comes closest to a complete record, and its record serves as the template for new benchmarks:

```yaml
question: "How much of peak memory bandwidth is achieved for sequential
           partial-line, sequential full-line, and random access?"
hardware:
  cpu_model: "unrecorded (Apple Silicon-class laptop)"  # <- still a gap
  memory: {size: "24 GB", type: "LPDDR5", channels: "unrecorded"}
compiler:
  toolchain: "clang"
  flags: "-O3 -Wall -std=c11 -march=armv8.5-a+simd"
evidence_class: wall-clock
method:
  repetitions: 5
  warmup: true  # buffer touched with memset before timing
  variance_reported: false  # <- gap: only the average of 5 passes is kept
workload:
  description: "1 GB buffer, three access patterns (seq8, seq64, rand8)"
  size_or_shape: "1 GB, 64 B cache lines"
results:
  raw_or_summary_table: "seq8 ~1/8 peak, seq64 ~55 GB/s, rand8 ~70 MB/s"
  units: "GB/s"
```

The largest gap in this record, the absence of per-pass variance, can be closed without an expensive rerun by reporting the min/max or standard deviation across the 5 passes instead of only the mean. Five samples are enough to give some indication of noise, but the current note discards that information.

## Applying this to RTL evidence

The RTL-waveform evidence class requires a field that the schema does not specify for the wall-clock and hardware-counter cases: the exact commit SHA of the RTL under test, together with the simulator and its version, because "cycles to execute this trace" is meaningful only when pinned to both. [[hardware/computer-architecture/rtl-reading-lab|The RTL reading lab]] pins every excerpt to a commit SHA for this reason, although it runs no simulations itself. A future benchmark note built on those cores (for example, one comparing branch misprediction recovery cycles between BOOM and XiangShan via waveform traces) should pin commits in the same way and also record the simulator name and the flags used to build the design.

## Edge cases and limits

The schema is informal by design (YAML-shaped prose, not a JSON Schema with a validator), because `.notes/` has no tooling to enforce measurement-record structure yet. It is a checklist for the author to complete before publishing a benchmark note and is not checked by machine. A future version could become a schema file under `.notes/`, alongside `frontmatter.yml`, `content.yml`, and `prose.yml`, referenced from the benchmark-note workflow in `AGENTS.md`; that change concerns the repository's infrastructure.

The schema also does not fully cover comparative benchmarking across systems with different ISAs (for example, comparing an x86 result with a result from RVV hardware), since cycle counts and even the meaning of "one operation" differ across ISAs in ways that a single `hardware.cpu_model` field cannot capture. The schema can be extended for this case when such a comparison is first attempted.
